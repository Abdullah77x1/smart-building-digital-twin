# Smart Building Digital Twin Dashboard

Hamad's dashboard component for the team's **Simulator V2 + Multi-Task Forecasting V1** repository. It runs locally and works offline once Python dependencies and the generated history are available.

## Start here

From the repository root (the folder containing `simulator`, `ml`, and `dashboard`):

```bash
python -m pip install -r requirements.txt
python simulator/building_simulator.py
python dashboard/app.py
```

Open **http://127.0.0.1:8050** in a modern browser. Keep the terminal running; Ctrl+C stops the server. On macOS, use `python3` if `python` is unavailable. No npm, API key, paid service, CDN, or cloud hosting is required.

The simulator writes the official 2022–2025 history locally. It is about 80 MB and is intentionally ignored by Git. This is a one-time setup; do not regenerate it on every launch. The eight-row example CSV is discontinuous and cannot support this dashboard or the ML lags.

### Existing local setup on Hamad's Mac

The environment and full dataset were prepared during dashboard development. Double-click `dashboard/launch.command`, or run:

```bash
.venv/bin/python dashboard/app.py
```

If port 8050 is busy, use `python dashboard/app.py --port 8051` and visit the printed address. To use another **compatible Simulator V2** CSV, pass `--csv data/your_history.csv`. Restart after changing the CSV or checkpoint; the service caches them in memory. Alternate histories must use the configured zone, uninterrupted five-minute timestamps and the documented columns. It is not a generic CU-BEMS importer.

### Windows virtual environment

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe simulator/building_simulator.py
.\.venv\Scripts\python.exe dashboard/app.py
```

Using the Python executable directly avoids PowerShell activation-policy issues. After setup, `dashboard/launch.bat` starts it again.

## What is implemented

| Screen | Working behavior |
| --- | --- |
| Overview | Inclusive date filtering; total/HVAC energy; load breakdown; indoor/outdoor temperature; occupied comfort; occupancy; hover values; raw CSV download |
| Forecasts | Real inference with `ml/results/multitask_model.pt`; 36 current/past features; three targets at +5/+10/+15/+30 minutes; exact future timestamp alignment; historical actuals and absolute error |
| Scenario lab | Calls the existing physics simulator twice with matched seed/weather/occupancy; adjustable setpoint shift and lighting policy; energy and occupied-comfort comparison; results CSV |
| Model & data | Dataset provenance, component availability, saved 2025 MAE/RMSE compared with no-change baseline, explicit limitations |

The LLM and optimization folders are not implemented by this dashboard. The overview summary is deterministic arithmetic and is labeled accordingly. The scenario candidate is selected by the user, not generated by an optimizer. This implements all four objectives in the original dashboard README without changing simulator or ML source.

## Data flow and calculations

```text
Generated CSV -> DashboardService -> /api/history -> overview charts and CSV export
Current/past CSV rows -> ml.make_features -> pretrained model -> /api/forecast
Scenario settings -> simulator.simulate (baseline + candidate) -> /api/scenario
Saved test_report.json -> /api/metrics -> evaluation table
```

- **Electrical power** is kW; it is not thermal cooling power and not kWh.
- Each record describes a five-minute interval. **Energy = sum(power × 5/60)**. KPIs sum the simulator's `energy_kwh` and `hvac_energy_kwh`, checked against the power columns.
- Dates are inclusive in the interface. Internally, `To + 1 day` is the exclusive end.
- Timestamps use the simulator's local, timezone-naive clock. The UI does not reinterpret them as UTC or the browser's timezone.
- Occupied comfort compliance = occupied intervals inside 23–26°C / all occupied intervals × 100. The band is the project's proxy, not a comprehensive comfort standard. With zero occupied intervals, the result is unavailable, not 100%.
- Charts use at most roughly 650 time bins, averaging power/temperature/occupancy per bin. KPIs and history downloads use every original row. The occupancy bar chart groups neighboring chart bins into at most 24 averages; its footer shows the nominal interval (the final bar can cover a shorter interval). Fractional occupancy in aggregated charts is an average.
- Forecast features use only rows from t−60 minutes through t. Future actuals are joined **after** inference. `next_indoor_temp_c` is never a model input. Lags cannot cross a year boundary.
- Forecast occupancy is a continuous estimate. The UI does not disguise fractional estimates as measured head counts.
- Scenario baseline and candidate use the same seed (42), config and exogenous drivers. The candidate policy also applies during its own seven-day warm-up, so initial temperatures can differ. This is a steady-policy experiment, not an instantaneous intervention at an observation timestamp.
- Scenario baseline is regenerated for the chosen period. It is not guaranteed identical to an arbitrary imported history with different parameters or seed. Its source and assumptions are shown beside the result.
- History ranges are limited to 366 days; scenarios to 31 days. Longer historical data remain loaded and can be explored through different ranges.

## Interfaces for teammates

`dashboard/service.py` is the integration boundary; HTML/JS never imports Python model details. The HTTP server only exposes an allowlist of static assets and API routes and binds to `127.0.0.1`. It has no sensor/control endpoint and accepts no arbitrary file path from a browser. Keep it local; the Python development server is not a production public hosting service.

| Endpoint | Input | Output |
| --- | --- | --- |
| GET `/api/meta` | none | Config, provenance, available dates and checkpoint presence |
| GET `/api/history` | `start`, `end` as ISO dates | Full-resolution summary plus chart series |
| GET `/api/export` | same dates | Original CSV rows |
| GET `/api/forecast` | `timestamp`, e.g. `2025-07-15T09:00` | Observation, four horizons, predictions and optional actuals |
| GET `/api/metrics` | none | Saved test report with training/validation split labels |
| POST `/api/scenario` | JSON: `start`, `end`, `shift` (−3..3), `lighting` (`scheduled` or `occupancy`) | Baseline/candidate series, energy differences, comfort results, provenance |

To connect the optimization teammate's future module, add an adapter that returns a selected candidate **plus its constraints, baseline, evaluation period and numerical results**. Keep optimization results separate from user-entered scenarios. To add an LLM later, pass these calculated results and limitations to the LLM on the server; label generated explanations, preserve numerical provenance, and never put API keys in frontend JavaScript. Neither integration is claimed complete here.

## Verification

```bash
python -m unittest discover -s dashboard/tests -v
```

Ten integration tests verify energy arithmetic, inclusive dates and export, unavailable comfort, invalid input, discontinuous/missing data, all forecast outputs, exact historical alignment, independence from future observations, identity scenarios, matched external drivers, comfort trade-offs, HTTP routes and cross-origin rejection. Requires the existing project dependencies; tests generate their own small temporary dataset. The checkpoint is read with `weights_only=True` through the team's unchanged loader.

A browser pass also covered navigation, real forecast inference, scenario execution, history filters, model metrics and error display. The layout has narrow-screen CSS and no remote asset dependency.

## Team review and contribution workflow

Read [IMPLEMENTATION_OUTLINE.md](IMPLEMENTATION_OUTLINE.md) for the development steps, file map and evidence, and [DEMO_GUIDE.md](DEMO_GUIDE.md) for the presentation walkthrough. The dashboard was developed with implementation assistance and integrates the team's existing simulator and ML work.

Work on a separate branch based on the team's current `main`, commit only intended dashboard changes, run the tests, and open a pull request. Teammates review and approve before merging. Do not commit `.venv`, generated history, private chat exports or project attachments.

The first local development copy came from a GitHub ZIP and has snapshot-only local ancestry. Do not push that local branch directly. The review submission is built on the actual upstream commit history and only includes `dashboard/` files. For future work, use an authenticated clone of the review branch.

## Typography

Source Sans 3 is bundled locally in `dashboard/static/fonts/` under the included SIL Open Font License. The UI uses lining, tabular numerals for consistent numeric alignment, including tables and chart labels. It requires no external font service.
